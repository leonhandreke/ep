# EP — macOS app plan

The app is a native macOS client for the EP backend (`server/`). Read these first:

- `plans/frontend-design.md` — the design, distilled from the user's Claude Design
  boards. It is the source of truth for layout, tokens, components, copy and shortcuts.
- `plans/frontend-design-handover.md` — the original brief (intent and vocabulary).
- `plans/backend.md` and `server/README.md` — the backend and its API conventions.
- `server/openapi.json` — the API contract the client is generated from.

## Instructions from the user

- Build in stages with Opus 5.5 subagents (medium effort), one after another, each
  followed by a separate reviewer subagent. Commit at reasonable intervals.
- An early stage builds a harness to take screenshots of the app and test it, modelled
  on the one in `~/Development/transmission-remote-gtk` (see "Harness reference" in
  `plans/frontend-design.md`). Use the harness very sparingly. Any testing with it is
  done by Sonnet subagents.
- Use the latest versions and current conventions; no backward-compat.
- Backend and app work in harmony. Neither side works around a shortcoming of the
  other. An app agent that finds the API awkward, missing something, or shaped wrongly
  for the UI does not patch around it in Swift: it reports it under "Backend friction"
  and a backend agent fixes it at the source.

## Principles

- A clean, client-neutral API comes first. The user, verbatim: "when deciding between
  a non-standard behavior or workaround on the swift vs. the API side, choose Swift.
  There will be other clients in the future, and those will benefit from the thing
  not being overfit to Swift." So: a missing capability or a server-side fact the UI
  needs is backend friction and gets fixed in the backend; an awkwardness that exists
  only because of Swift or its OpenAPI generator (explicit nulls in PATCH, date
  parsing, naming) is handled in Swift.
- The design is followed as drawn. Where it is silent or contradicts itself, use the
  decisions below; where those are silent, follow macOS conventions and say what you
  chose in your report.
- Plain architecture. No abstraction without a second user. No client-side database,
  no disk cache, no sync engine.
- The server is the only source of truth. There is no realtime push: views reload on
  navigation, after the user's own actions, when the window becomes active, and by
  polling only where the design needs it (running imports).
- Never write to audio files. The app never touches `~/Music/Library`.
- Every interactive control gets a stable accessibility identifier (the harness finds
  controls by identifier, not coordinates) and a VoiceOver label.

## Toolchain

- Xcode 26.3 (the newest Xcode that runs on this Mac's macOS 15.8): Swift 6.2, macOS
  26.2 SDK. Deployment target: macOS 15. APIs that exist only on macOS 26 are used
  behind availability checks only where they degrade gracefully.
- An Xcode project in `app/` using buildable folders (file-system-synchronised groups),
  so adding a source file never means editing the project file. Built and tested from
  the command line with `xcodebuild`. Swift 6 language mode, strict concurrency,
  approachable-concurrency defaults (main-actor isolation by default for the app
  target).
- Use the most modern approach available for everything: Swift Testing for unit tests,
  XCUITest (`xcodebuild test`) for UI automation and screenshots. The harness in
  `transmission-remote-gtk` is a reference for ideas only (private seeded backend,
  isolated settings, agent guide); do not copy its hand-rolled event driver where
  XCUITest does the job.

## Tech choices

- SwiftUI with the Observation framework (`@Observable`); AppKit only where SwiftUI
  cannot do the job (the note editor's text view, some window and event handling).
- API client generated by `swift-openapi-generator` (SwiftPM build plugin) from
  `server/openapi.json`, with the URLSession transport. No hand-written DTOs. Where
  the generated client is awkward for a standard API feature (e.g. sending an explicit
  `null` in a PATCH to clear a field), add a small Swift-side helper; do not ask the
  API to change.
- Playback: AVFoundation (`AVPlayer`) streaming `GET /sources/{id}/stream` (HTTP
  Range). Slices are played by seeking within the file using the start/end the API
  returns. Now Playing info and media keys via MediaPlayer.
- Note editor: an `NSTextView` (TextKit 2) wrapped for SwiftUI, with live-preview
  Markdown styling. Link and highlight ranges from the API are UTF-16 offsets and map
  directly to `NSRange`.
- Tests: Swift Testing for models, stores and the Markdown/link logic, against a
  stubbed transport. UI is checked with the harness (XCUITest).

```
app/
  EP.xcodeproj
  EP/                    # the app target (App, Stores, Views by feature, Player, NoteEditor)
  EPTests/               # Swift Testing
  EPUITests/             # XCUITest harness
  Packages/              # local Swift packages only where a split earns its keep
                         # (e.g. the generated API client)
  scripts/               # build, run, ui-test wrappers for agents
```

## Decisions on points the design leaves open

1. **Detail panels.** Library: three panels side by side (artist, album, track), each
   with stacked Note / Tags / Linked from sections, one shared divider, collapsible
   (⌥⌘D), as drawn. Radio: one full-width tabbed panel for the selected episode (or
   show when no episode is selected), as drawn.
2. **Accent colour.** Follow the system accent colour; the design's blue is the
   default look.
3. **Player bar right side.** Volume, queue button with count, "Show playing" (⌘L).
4. **Note headings.** H1 22, H2 18, H3 15.
5. **Narrow windows.** Use the design's minimum column widths; the window's minimum
   size is their sum. No column collapsing.
6. **Opening things.** Sources popover: click the track's state icon, or context menu
   → "Sources…". Edit sheet: context menu → "Edit…" and ⌘E on the selection.
7. **Tag click.** Opens the search palette pre-filtered to that tag.
8. **Queue.** A popover from the queue button: upcoming items, remove, clear.
9. **Search shortcuts.** ⌘K and ⌘F both open the palette.
10. **Review questions not drawn** (artist choice, release-group choice, MusicBrainz
    release choice, release conflict, download or fetch failures): same list + detail
    layout as the drawn "same recording" question, driven by the issue's kind,
    candidates and choices from the API. Unknown issue kinds render generically from
    message + choices, so new backend kinds never break the sheet.
11. **Failed jobs.** Retry and Dismiss on the job row.
12. **Server unreachable.** What is already loaded in memory stays visible; notes
    become read-only; retry with a countdown, as drawn. Nothing is cached on disk, so
    a cold start without a server shows the unreachable state with no data.
13. **Multiple windows.** ⌥⌘-click opens the target in a new main window. Each window
    has its own navigation history; all share one player.
14. **Dark appearance.** Derived from the design's dark tokens and system materials.
15. **Standalone notes, playlists, cover grid.** Out of scope.

## Stages

Each stage: an implementer, then a reviewer. Every report includes a "Backend
friction" section (may be empty). Harness checks are run by a Sonnet subagent, only at
the points marked ⟡, and only for what unit tests cannot show.

0. **Backend fit pass** (backend agent). Compare `plans/frontend-design.md` with the
   API and close the gaps before any Swift is written: whatever the designed screens
   need that the API does not offer or offers awkwardly (candidates: server version and
   library counts for Settings; file-missing state in playback info; cancelling a
   running job; partial retry; counts for the artist filter, hidden radio-only artists
   and album headers; grouped search results with radio match positions; tag filter in
   search). Commit `server/openapi.json`, with a test that fails when it is stale.
   Add a seed command that fills a scratch database with a small, fixed demo library
   (artists, albums of each kind, loose tracks, a single-file album, a radio show with
   an episode, notes with links, tags, import jobs in each state) and generated audio,
   for the harness and for development.
1. **Scaffold.** Xcode project, build and run scripts, generated client, app shell: main
   window with toolbar and empty three-column frame, design tokens as Swift constants,
   server address setting, connection state. Building, unit tests and the app
   launching are verified from the command line.
2. **Harness.** `app/scripts/ui-test/`: start a private backend (compose project with
   its own database and ports, seeded by the stage 0 command), launch the app against
   it with isolated settings via XCUITest, drive it by accessibility identifier, take
   screenshots as test attachments exported to a folder, assert on app and backend
   state, tear down. A
   short guide for agents on how and when to use it. ⟡ one smoke run.
3. **Library browsing.** Artists (filter, radio-only toggle, type-to-select), release
   groups (covers, loose tracks entry), tracks (all track states, disc headings),
   column headers, keyboard navigation, navigation history with back/forward. ⟡
4. **Player.** Transport, scrubber, volume, queue, play album, slices, long files with
   tracklist marks and estimated marks, link-only and nothing-playing states, Show
   playing, media keys. ⟡
5. **Detail panels.** Tags (add with autocomplete, remove, counts), Linked from
   (backlinks with snippets, radio appearances with play-from-here), read-only note
   rendering as a placeholder for stage 6, collapse and resize.
6. **Note editor.** Live-preview Markdown, links as chips, `[[` autocomplete with
   covers, ⌘-hold link navigation, ⌥⌘-click new window, broken links, autosave with
   conflict handling (409), no-match actions. ⟡
7. **Radio view.** Shows, episodes, tracklist, tabbed panel, play from entry,
   re-pointing an entry.
8. **Search, sources, editing.** Search palette (grouped results, play, play next,
   copy link), sources popover (preferred source, Locate…, add source), edit sheets
   (album, artist, track; credits; cover drop; track reorder), create by hand.
9. **Import.** Import sheet (link field with kind detection, folder drop, ⌘V anywhere),
   job queue with progress and log, review sheet (keyboard-driven, all issue kinds),
   toolbar badge, toast, ⇧⌘I, polling while jobs run. ⟡
10. **Settings, states, polish.** Settings (server, watched folders), empty library,
    server unreachable, loading skeletons, dark appearance, menus, a full keyboard and
    VoiceOver pass. ⟡ final pass over every designed board.

## Report format for app agents

At most 15 lines: what was built; decisions made where the design or this plan was
silent; test results; commit hashes; **Backend friction** (each item: what the UI
needs, what the API gives, the change you would make to the backend); anything
unverified.
